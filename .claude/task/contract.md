decisions_reserved:
  - **Update-mechanism scope: a minimal version stamp, not a port of
    `dbt-agent-kit`'s `sync-base.sh`/`check-sync-coverage.py`/`.base-version`
    machinery.** Decided during Phase 7 planning, after directly reading
    `dbt-agent-kit`'s actual sync mechanism. That machinery (merge logic for
    composed files, a coverage guard, a CI drift-check workflow) exists because
    `dbt-agent-kit` is a DERIVATIVE kit — it layers its own local
    reviewers/routing overlay (`.claude/routing.dbt.json`,
    `.claude/working-agreement.dbt.md`) on top of `claude-guardrails` and needs
    to preserve that overlay while pulling in base updates. A plain project
    generated by THIS kit's own `scripts/generate_project_setup.py` has no such
    local kit-file overlay — its `.claude/agents/*.md` and `review_routing.json`
    are pure generated output. For that case, updating is already fully solved
    by re-running two things that already exist and already work:
    `scripts/bootstrap.sh` (blindly refreshes `.claude/{hooks,agents,commands,
    skills,tests}`) and `scripts/generate_project_setup.py --force` (re-applies
    routing/guard-paths; already refuses to silently clobber a hand-customized
    file without `--force`). Porting the full `sync-base.sh` pattern would add
    real machinery to solve a merge problem this kit's own generated projects
    don't have. So `bootstrap.sh` gains only a version stamp; the update path is
    documented in `README.md`, not built as new tooling. If derivative kits
    become a repeated pattern later, a real sync mechanism can be built then.
  - **`bootstrap.sh` does NOT gain `refresh_dir "templates"`** (revises the
    master plan's original Phase 7 wording). `templates/` is read directly by
    `generate_project_setup.py` from the kit checkout at generation time —
    `.claude/skills/setup-project/SKILL.md` already documents that the
    interview "only works from a `claude-guardrails` checkout." Nothing in a
    bootstrapped/generated project ever reads a local copy of `templates/`.
    Copying it would dump two kit-maintainer-only files
    (`templates/reviewers/README.md`, `templates/reviewers/routing/README.md`
    — they document the module library itself and reference
    `scripts/lint_reviewer_name.py`, meaningless without the kit's own
    `scripts/`, which `bootstrap.sh` has never copied either) plus every
    unselected reviewer draft into every consumer repo, for no functional
    reason.
  - `.claude/.kit-version` is always refreshed on every `bootstrap.sh` run
    (like the other "kit code" paths — `.claude/hooks`, `.claude/agents`,
    etc.), never treated as project-owned/`keep_file` config — it's a fact
    about which kit version was last used to bootstrap/refresh the project,
    not something a project customizes.
  - `docs/decisions/*.md` ADRs are short and point at their existing source
    (a phase's plan section, contract, or `.claude/rules/guard-paths.md`'s own
    text) rather than re-narrating the full history — matching this repo's
    own established aversion to `football-data-pipeline`'s inline JSON `_doc`
    essays, which cost real review-round loops re-litigating prose embedded in
    config.

done_when:
  - `scripts/bootstrap.sh`: after the existing kit-code refresh block (the
    `refresh_dir`/`refresh_file` calls), writes `.claude/.kit-version` —
    `git -C "$KIT_ROOT" rev-parse HEAD` (this kit's own current commit SHA,
    the checkout `bootstrap.sh` is being run from), one line, unconditionally
    overwritten on every run, respecting `--dry-run`. `--force` has no
    special effect on it (it's already always-refreshed, matching kit-code
    paths, not `keep_file` paths).
  - `.claude/tests/test_bootstrap.py`: `_EXPECTED` (or an equivalent explicit
    check) confirms `.claude/.kit-version` exists after a fresh bootstrap and
    its content looks like a full 40-hex-char git SHA; a re-run test confirms
    it's overwritten (not preserved like project-owned config) if the kit's
    own HEAD has moved between runs — or, at minimum, confirms it is written
    fresh every run rather than skipped when already present.
  - `README.md`: "What's in the repo" rewritten to reflect current reality —
    the reviewer-module library (`templates/reviewers/*`, currently 5
    modules + `_skeleton.md`), the composition/naming tooling
    (`scripts/compose_routing.py`, `scripts/lint_reviewer_name.py`,
    `scripts/promote_reviewer.py`), the `setup-project` interview
    (`scripts/preview_project_setup.py`, `scripts/generate_project_setup.py`,
    `.claude/skills/setup-project/SKILL.md`), and the CI-automation audit
    (`scripts/audit_ci_automation.py`) — not just "the two reviewers
    (`scope-auditor`, `cto-reviewer`)." "Add it to a repo" gains a short
    paragraph on the update path: re-run `bootstrap.sh` (kit code refresh)
    and, if the project was generated via the interview, re-run
    `generate_project_setup.py --force` to re-apply routing/guard-paths: no
    reproduction of contract prose is embedded in the README itself.
  - `docs/project-kit-design.md`: a real overview aimed at someone sizing up
    the kit — the module-library architecture (why hand-authored modules,
    not template parameter-substitution — pointer to its own ADR), how
    `scripts/`/`templates/`/`.claude/` fit together, the review-gate
    mechanics (blinded reviewers, the round cap, guard-paths escalation).
    Distinct from `README.md`'s "how do I use this" framing — this is "how
    does this work / why is it built this way."
  - `docs/decisions/*.md` — one file per real decision already made in this
    build, each pointing at its actual source rather than re-narrating it:
    `module-library-vs-templating.md` (Phase 1 of the master plan — a
    library of hand-authored modules, not synthesized-from-flags reviewers,
    because a generic reviewer reproduces the exact "one overloaded
    reviewer" failure `football-data-pipeline` already fixed once);
    `convention-vs-hook-model-routing.md` (Phase 4 / `.claude/rules/
    guard-paths.md`'s own "not hook-enforced" text — a `PreToolUse(Bash)`
    hook cannot see a Task-tool subagent spawn, so opus-on-guard-paths is a
    documented convention, not mechanically enforced); `advisory-vs-blocking-
    ci-audit.md` (Phase 5's contract — `scripts/audit_ci_automation.py`
    never auto-fixes branch protection/auto-merge settings, always
    advisory); `no-automated-confidentiality-collection.md` (Phase 6b's
    contract — the scope-doc/summarization feature was cut entirely, not
    deferred, and why); `minimal-version-stamp-vs-sync-mechanism.md` (this
    phase's own decision, recorded above in `decisions_reserved`).
  - All existing `.claude/tests/test_*.py` still pass; `bash -n
    scripts/bootstrap.sh` (syntax check) passes; no JSON/config file is
    touched by this contract at all.
  - Nothing under `.claude/hooks/`, `.claude/agents/`, `templates/`,
    `scripts/generate_project_setup.py`, `scripts/preview_project_setup.py`,
    or `scripts/compose_routing.py` is modified — additive/documentation
    only, plus the one `bootstrap.sh` addition described above.
  - scope-auditor + cto-reviewer (opus — diff touches `scripts/*` and

    1. `git -C "$KIT_ROOT" rev-parse HEAD` (no `--verify`) echoes the literal

       SHA, a valid-looking but completely wrong value. FIXED: only trust

       resolves to `$KIT_ROOT` itself.
