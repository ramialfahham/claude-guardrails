# A version stamp, not a ported sync-base.sh mechanism

**Status**: decided, shipped (Phase 7). Source: Phase 7's
`.claude/task/contract.md`.

## Context

The master plan's original Phase 7 wording called for `bootstrap.sh` to gain
"an update mechanism so already-scaffolded projects can pull in later kit
improvements," modeled on the sibling repo `dbt-agent-kit`'s
`sync-base.sh`/`check-sync-coverage.py`/`.base-version` machinery — a
hardcoded verbatim-file list, hand-written merge logic for two "composed"
files, a coverage guard that fails on new upstream files, and a CI job that
re-syncs against a pinned commit to detect drift.

## Decision

`bootstrap.sh` gains only a version stamp: `.claude/.kit-version`, this kit's
own `git rev-parse HEAD`, rewritten on every run. No merge-logic script, no
coverage guard, no CI drift-check template. "Updating" a bootstrapped or
generated project is: re-run `bootstrap.sh` (already refreshes
`.claude/{hooks,agents,commands,skills,tests}` unconditionally) and, if the
project went through the interview, re-run
`scripts/generate_project_setup.py --force` (already refuses to silently
clobber a hand-customized `review_routing.json`/`guard-paths.md` without
`--force`) — both already existed and already worked before this phase.

## Why

`dbt-agent-kit` needs the fuller machinery because it is a *derivative* kit —
it layers its own local reviewer/routing overlay
(`.claude/routing.dbt.json`, `.claude/working-agreement.dbt.md`) on top of
this kit and has to preserve that overlay while pulling in base updates,
which is exactly what its "composed file" merge logic and coverage guard
exist to protect. A plain project generated by this kit's own tooling has no
such local kit-file overlay to preserve — its `.claude/agents/*.md` and
`review_routing.json` are pure generated output, nothing hand-layered in.
Porting the fuller pattern would add real, ongoing-maintenance machinery (a
file list to keep in sync by hand, a coverage guard, a CI workflow template)
to solve a merge problem this kit's own generated projects don't actually
have.

## Consequences

- A project owner can tell what kit version they're on
  (`.claude/.kit-version`) but there's no automated drift detection or
  coverage guard — if this kit adds a new file class that a re-run of
  `bootstrap.sh`/`generate_project_setup.py` wouldn't naturally pick up,
  nothing currently catches that silently.
- If derivative kits (repos that extend this one with their own local
  overlay, the way `dbt-agent-kit` does) become a repeated pattern, a real
  sync mechanism — closer to `dbt-agent-kit`'s own — earns its complexity
  then, for that specific case, rather than being built preemptively here.
- **The "already fully solved" claim above has a real gap, caught in this
  phase's own review**: `generate_project_setup.py` doesn't persist WHICH
  stack answers a project was originally generated with — only
  `.claude/.kit-version` (a kit commit SHA) is stamped, never the interview's
  own flags. Re-running it later to update requires the owner to remember
  and re-supply the same `--dbt`/`--data-eng`/etc. flags by hand; passing
  none (the default) or the wrong ones silently REDUCES the reviewer set on
  a `--force` re-run, rather than refreshing it. This isn't fixed here —
  fixing it properly means persisting the original answers somewhere
  durable (a manifest, or reconstructing them from the composed
  `review_routing.json`, which `scripts/generate_project_setup.py`'s own
  provenance-marker precedent could extend to) — real, scoped work, not a
  docs fix. Documented as a known limitation (`README.md`'s "Pulling in
  later kit improvements" section says so explicitly) rather than silently
  left for someone to discover the hard way.
